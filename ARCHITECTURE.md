# Архитектура проекта NTC

## 1. Цель и подход

Проект NTC (Network Traffic Controller) представляет собой десктопное приложение на Python с GUI на PyQt6 для мониторинга сетевой активности приложений, ведения чёрного списка и блокировки сетевого трафика, а также уведомления пользователя о попытках соединения заблокированных приложений.

Архитектура построена на принципах MVC, но с добавлением сервисного и инфраструктурного слоёв, поскольку мониторинг, блокировка трафика, работа с БД и платформенными API выходят за рамки классической модели "View-Model-Controller" и требуют более гибкой структуры.

Основной принцип:
- UI отвечает только за отображение и обработку ввода;
- бизнес-логика вынесена в сервисы и доменные сущности;
- платформенные особенности реализованы через адаптеры;
- мониторинг, блокировка и уведомления работают асинхронно в фоне.

---

## 2. Общая архитектура

### 2.1. Компоненты системы

Приложение состоит из следующих логических уровней:

1. Presentation Layer (UI)
   - Главное окно приложения;
   - Диалог чёрного списка;
   - Окно настроек;
   - Уведомления и системный трей;
   - Виджеты мониторинга и графиков.

2. Application Layer (Controller / Coordination)
   - Управление жизненным циклом приложения;
   - Связь между UI и бизнес-логикой;
   - Запуск и остановка мониторинга;
   - Передача событий между слоями;
   - Координация блокировки и уведомлений.

3. Domain Layer
   - Пр��вила чёрного списка;
   - Проверка соединений against policy;
   - Расчёт трафика;
   - Формирование событий и инцидентов;
   - Логика уведомлений и блокировок.

4. Infrastructure Layer
   - Работа с SQLite;
   - Хранение настроек;
   - Сбор данных через psutil;
   - Работа с системным файрволом (Windows/Linux);
   - Уведомления ОС и GUI;
   - Адаптеры для разных платформ.

## 3. Логическая структура проекта

### 3.1. UI-компоненты

#### Главное окно
- Таблица активных сетевых соединений;
- Список процессов и их метрик;
- Кнопки: обновить, очистить, настройки;
- Статусная строка с общей статистикой;
- График трафика или индикаторы активности;
- Отображение текущего состояния блокировки.

#### Диалог управления чёрным списком
- Список правил;
- Форма добавления нового правила;
- Редактирование существующих записей;
- Удаление правил;
- Подтверждение применения списка.

#### Окно настроек
- Частота обновления;
- Включение/выключение уведомлений;
- Выбор режима работы;
- Параметры хранения логов и истории;
- Платформенные параметры для файрвола.

#### Система уведомлений
- Toast-уведомления или системный трей;
- Показ события без перехвата фокуса;
- Возможность отключения оповещений по отдельным приложениям или глобально.

---

### 3.2. Контроллеры и координаторы

#### AppController
- Инициализация приложения;
- Загрузка конфигурации;
- Подключение модели и сервисов;
- Запуск мониторинга;
- Обработка пользовательских действий.

#### MonitoringController
- Запускает цикл сбора данных;
- Получает информацию о сетевых соеди��ениях;
- Передаёт данные в сервисы анализа;
- Запускает проверки на соответствие чёрному списку.

#### BlacklistController
- CRUD-операции над правилами;
- Валидация вводимых значений;
- Синхронизация с БД;
- Передача актуальных правил в ядро фильтрации.

#### FirewallController
- Аппаратная/сетевое применение правил;
- Обработка блокировок/пропусков;
- Передача сигнала в систему уведомлений и логирование инцидентов.

---

### 3.3. Доменные сущности

#### ProcessRecord
- PID;
- имя процесса;
- путь к исполняемому файлу;
- список активных соединений;
- состояние процесса.

#### NetworkConnectionRecord
- локальный адрес и порт;
- удалённый адрес и порт;
- протокол;
- статус подключения;
- объём отправленных/полученных данных;
- метка времени.

#### BlacklistRule
- идентификатор;
- тип правила: процесс, IP, домен;
- значение правила;
- флаг активности;
- дата создания/редактирования.

#### TrafficStat
- общий объём входящего/исходящего трафика;
- скорость трафика;
- число активных соединений;
- статистика по конкретному процессу или приложению.

#### IncidentLog
- дата и время события;
- имя процесса;
- удалённый IP и порт;
- тип совпавшего правила;
- действие: "блокировано", "предупреждено", "игнорировано".

## 4. Сервисы системы

### 4.1. ProcessMonitorService
Отвечает за мониторинг процессов и сетевых соединений.

Основные задачи:
- сбор списка сетевых соединений;
- сопоставление PID и имени процесса;
- выявление активных приложений;
- анализ трафика по процессам;
- расчёт дельт между опросами.

### 4.2. TrafficAnalyzerService
Отвечает за агрегирование метрик и подготовку данных для UI.

Основные задачи:
- расчёт объёма и скорости трафика;
- агрегация по процессам и приложениям;
- формирование статистики для таблицы и графиков;
- вычисление максимумов, средних и общих значений.

### 4.3. BlacklistService
Отвечает за управление политикой блокировки.

Основные задачи:
- CRUD для чёрного списка;
- проверка нового соединения на наличие правила;
- поддержка различных типов правил;
- хранение и загрузка правил из БД.

### 4.4. FirewallService
Отвечает за реализацию блокировки трафика.

Основные задачи:
- блокировка соединений приложений из чёрного списка;
- работа в режиме "мониторинг + блокировка";
- обработка исключений при отсутствии прав администратора;
- адаптация под Windows и Linux.

### 4.5. NotificationService
Отвечает за доставку уведомлений пользователю.

Основные задачи:
- генерация события о попытке соединения;
- создание информативного уведомления;
- поддержка глобального и локального отключения;
- отображение через tray, toast или системный механизм ОС.

### 4.6. PersistenceService
Отвечает за хранение данных между сеансами.

Основные задачи:
- сохранение списка правил;
- хранение истории инцидентов;
- сохранение настроек;
- загрузка параметров при старте приложения.

## 5. Хранение данных

### 5.1. База данных
Основным решением является SQLite, так как:
- приложение локальное;
- данные небольшие и структурированные;
- легко хранить правила и события;
- удобно реализовывать CRUD;
- нет необходимости в серверной инфраструктуре.

### 5.2. Рекомендуемые таблицы
- blacklist_rules
  - id
  - rule_type
  - rule_value
  - enabled
  - created_at
  - updated_at

- incidents
  - id
  - timestamp
  - process_name
  - pid
  - target_ip
  - target_port
  - rule_type
  - action

- settings
  - key
  - value
  - updated_at

- traffic_history
  - id
  - timestamp
  - process_name
  - bytes_sent
  - bytes_recv
  - active_connections

### 5.3. JSON
JSON можно использовать для:
- настроек пользователя;
- хранения небольших конфигурационных параметров;
- промежуточного кэша, если требуется резервный формат.

## 6. Платформенные адаптеры

Согласно ТЗ, реализация блокировки трафика существенно отличается на Windows и Linux.

### 6.1. Windows
Возможные реализации:
- pydivert;
- netsh advfirewall;
- блокировка на уровне соединений, а не остановка процесса.

### 6.2. Linux
Возможные реализации:
- iptables;
- nftables;
- python-iptables / subprocess + firewall tools.

### 6.3. Роль адаптеров
Адаптеры обеспечивают единый интерфейс для сервиса блокировки, скрывая платформенную реализацию:
- WindowsAdapter;
- LinuxAdapter;
- AdapterFactory.

Это позволяет основной бизнес-логике не зависеть от конкретной ОС и не разрастаться в условные конструкции.

## 7. Потоки и параллельность

Проект должен быть отзывчивым даже при активном мониторинге. Поэтому архитектура предполагает несколько потоков.

### 7.1. UI-поток
- отображение окна приложения;
- обработка событий пользователя;
- обновление таблиц, графиков и статуса.

### 7.2. Поток мониторинга
- опрос сетевых соединений;
- сбор метрик;
- рассчёт дельт трафика;
- подготовка данных для модели.

### 7.3. Поток блокировки
- применение правил в файрволе;
- блокировка по��ыток соединения;
- операция должна происходить независимо от интерфейса.

### 7.4. Поток уведомлений
- формирование уведомлений;
- отображение всплывающих окон;
- логирование срабатываний.

Это соответствует ТЗ и уменьшает вероятность зависания интерфейса во время активного мониторинга.

## 8. Алгоритм работы приложения

1. Запуск приложения.
2. Загрузка настроек и списка правил чёрного списка.
3. Инициализация UI и сервисов.
4. Старт потока мониторинга.
5. Сбор данных о сетевых соединениях в реальном времени.
6. Сопоставление соединений с процессами по PID.
7. Расчёт метрик трафика и статистики.
8. Сравнение соединений с чёрным списком.
9. При совпадении:
   - формируется инцидент;
   - применяется блокировка соединения;
   - отправляется уведомление;
   - запись сохраняется в БД.
10. Обновление данных в таблице и графике.
11. При изменении настроек или правил — синхронизация с БД и применяемыми политиками.

## 9. Взаимодействие слоёв

### 9.1. Схема взаимодействия
- UI → Controller: события пользователя;
- Controller → Service: команды запуска/остановки, изменение настроек, добавление правил;
- Service → Domain: проверка и расчёт логики;
- Domain → Infrastructure: сохранение в БД, вызов OS APIs, отправка уведомлений;
- Infrastructure → UI: сигналы обновления модели и состояния.

### 9.2. Принцип слабой связанности
- UI не должен напрямую обращаться к psutil;
- сервисы не должны напрямую создавать виджеты;
- бэкенд блокировки не должен знать про интерфейс приложения;
- логика доступа к данным вынесена в слой хранения.

## 10. Основные риски и ограничения

### 10.1. Права доступа
Для блокировки трафика на Windows и Linux необходимы права администратора или специальные привилегии:
- Windows: WinDivert/администратор;
- Linux: CAP_NET_ADMIN или эквивалентные разрешения.

### 10.2. Ограничение по домену
Блокировка по домену не является простой задачей: она требует анализа DNS, SNI или иных сетевых метаданных. Поэтому в первой версии допустимо ограничиться:
- процессами;
- IP-адресами;
- частично доменами при наличии отдельных механизмов.

### 10.3. Производительность
- опрос сети должен выполняться не чаще 1–2 раз в секунду;
- нужно избегать чрезмерной нагрузки на UI;
- статические данные следует кэшировать.

### 10.4. Обход блокировки
Некоторые процессы могут использовать нестандартные сокеты или сетевой стек, поэтому защита не гарантирует абсолютную блокировку в каждом сегменте.

## 11. Требования к чистоте архитектуры

Чтобы проект оставался поддерживаемым:
- выделить отдельные пакеты для UI, контроллеров, сервисов, моделей и инфраструктуры;
- держать доменную логику вне UI;
- делать платформенные отличия в адаптерах;
- централизовать логирование и обработку ошибок;
- использовать сигналы/события вместо прямых вызовов между потоками.

## 14. Итоговая архитектурная рекомендация

Наиболее правильная архитектура для NTC:
- MVC как базовая концепция;
- service layer как ядро предметной логики;
- platform adapters для OS-specific фун��ционала;
- SQLite для хранения правил и событий;
- многопоточный мониторинг и блокировка;
- event-driven взаимодействие между UI и сервисами;
- отделение инфраструктуры от пользовательского интерфейса.

Такая структура соответствует ТЗ, обеспечивает масштабируемость, упрощает поддержку и позволяет комфортно реализовать поддержку Windows и Linux в рамках одной кодовой базы.

## 15. Краткое резюме

Проект NTC должен быть реализован как локальное десктопное приложение с чётким разделением на:
- UI;
- контроллеры;
- бизнес-сервисы;
- модели и сущности;
- инфраструктуру хранения и сетевых операций;
- платформенные адаптеры.

Это даст чистую архитектуру, устойчивую к изменениям, простую в сопровождении и соответствующую функциональному заданию.
